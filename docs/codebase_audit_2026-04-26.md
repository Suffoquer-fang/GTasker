# GTasker 代码库巡检报告（2026-04-26）

> 范围：`gtasker/` 与 `tests/` 目录的静态审阅 + 基础测试执行（`pytest -q`）。

## 总览结论

当前项目核心功能思路清晰（任务抽象、RPC server、调度与 GPU 资源跟踪分层明确），但在**可维护性**、**并发安全**、**测试稳定性**和**接口兼容性**方面存在若干高优先级改进点。建议优先修复 P0/P1 问题后，再推进功能演进。

---

## P0（应优先修复）

### 1) 测试在收集阶段就失败，CI 不稳定
- 现象：`TaskScheduler.add_task` 需要 `env` 参数，但测试调用未提供，导致 `pytest` 收集阶段抛异常。
- 影响：测试套件无法稳定运行，回归风险不可控。
- 证据：`tests/test_scheduler.py` 中多处 `add_task(...)` 未传 `env`，并且文件底部存在直接调用测试函数。 
- 建议：
  1. 给 `TaskScheduler.add_task` 增加默认参数 `env=None`，内部归一化为 `{}`；
  2. 删除/改写测试文件底部直接调用，统一走 pytest 用例。

### 2) 可变默认参数导致潜在共享状态问题
- 现象：`Task.__init__` 中 `req_gpu_index=[]`, `pre_reqt=[]`, `env={}` 使用了可变默认值。
- 影响：多个实例可能意外共享同一对象，引发隐式状态污染，问题隐蔽且难排查。
- 建议：默认值改为 `None`，在构造函数中转换为新对象。

### 3) 锁管理使用手动 acquire/release，异常路径存在死锁风险
- 现象：调度与任务执行关键路径中大量手动 `mutex.acquire()`/`release()`。
- 影响：一旦中途异常（I/O、子进程创建、序列化错误等），可能遗漏 release，导致整个调度器卡死。
- 建议：统一改为 `with self.mutex:` / `with mutex:` 上下文管理。

---

## P1（建议尽快修复）

### 4) 任务依赖校验不完整，可能触发 KeyError 或逻辑异常
- 现象：`_check_pre_reqt` 直接访问 `self.tasks[pre_task_id]`，对不存在依赖未做保护。
- 影响：当依赖任务被删除、输入非法或迁移数据异常时，调度线程可能崩溃。
- 建议：
  - `add_task` 阶段校验依赖任务是否存在；
  - `_check_pre_reqt` 增加缺失依赖容错并输出可诊断日志。

### 5) CLI 调试输出依赖 `env["_"]`，存在 KeyError 风险
- 现象：`add_task_func` 中直接读取 `env["_"]` 并打印。
- 影响：在不同 shell/平台/启动方式下该变量可能不存在，导致命令失败。
- 建议：改为 `env.get("_", "")` 或移除该调试输出。

### 6) 日志/跟随输出函数混用 print 与 callback，接口语义不统一
- 现象：`utils.follow` 里先 `print` 最近几行，再对新增内容使用 `callback`。
- 影响：调用侧很难完全接管输出（比如 RPC/GUI 前端复用）。
- 建议：统一通过 callback 输出，print 仅用于 CLI 入口层。

## P2（中期优化）

### 7) 测试中存在硬编码本地路径，跨环境不可复现
- 现象：`ls_task()` 使用固定目录 `/home/fangyan/Workspace/ColBERT/`，测试里对其做断言。
- 影响：除作者机器外大概率失败，削弱测试可信度。
- 建议：使用临时目录（`tempfile.TemporaryDirectory`）与参数化工厂替代硬编码。

### 8) 测试文件中存在“导入即执行”代码
- 现象：多个测试文件底部直接调用测试函数。
- 影响：pytest 收集与执行边界被破坏，导致顺序依赖与副作用。
- 建议：删除底部直接调用，必要时改为 `if __name__ == "__main__":` 的示例脚本单独放置。

### 9) 调度策略可扩展性不足
- 现象：`_find_task_to_run` 按字典迭代顺序挑第一个可运行任务，未显式使用 `priority`。
- 影响：任务公平性/可预测性一般，优先级字段形同虚设。
- 建议：改用优先队列或按 `(priority desc, id asc)` 排序策略。

---

## 建议的分阶段落地计划

1. **第 1 周（稳定性）**：修复 P0（接口默认参数、可变默认值、锁上下文化）+ 让 pytest 先可跑。
2. **第 2 周（健壮性）**：完成 P1（依赖校验、CLI 环境变量防御、follow 输出一致化）。
3. **第 3 周（工程化）**：推进 P2（测试重构、调度策略升级、补充文档/CI）。

---

## 验证建议

- 最低门槛：`pytest -q` 在无 GPU、无特殊本地路径环境下可通过。
- 关键回归场景：
  1. 并发 add/kill/restart 不死锁；
  2. 非法依赖任务输入可返回友好错误；
  3. `gta add` 在不同 shell 环境下行为一致。
